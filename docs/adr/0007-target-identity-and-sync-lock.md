# ADR-0007: Идентичность target и сериализация sync

**Статус:** accepted
**Дата:** 2026-10-27

## Контекст

В глоссарии target описывался как пара «приложение + окружение + кластер», а в store уникальность задаётся парой `(app, target)`, кластер перезаписывается. Без явного решения #20 и схема store расходились.

Docker Swarm `ServiceUpdate` и `ConfigUpdate` в WormCD работают без optimistic lock (Version берётся из Inspect в момент Apply). Два параллельных sync одного target могут перезаписать результаты друг друга.

## Решение

1. **Target = `app/target`**, например `web/prod`. Уникальность — по `(app, target)`. В v0 target привязан ровно к одному кластеру; кластер — атрибут target, а не часть ключа. Имя target несёт окружение, поэтому `web/prod` и `web/staging` — разные target даже в одном кластере.
2. **Sync одного target сериализуется in-process mutex** по ключу `app/target` внутри `wormcd server`. Разные target синхронизируются параллельно.
3. Ограничение: допустим только один процесс `wormcd server` (ADR-0006: одна реплика). При переходе к нескольким процессам решение пересматривается.

4. **API в M1 слушает только loopback.** `wormcd server` отказывается запускаться с адресом не-loopback (`requireLoopback`). Токена в M1 нет: API не аутентифицирует клиентов, защищает только адрес и проверки Host/Origin. Аутентификация (bearer token) вынесена в отдельный issue; не-loopback адрес разрешается только после неё.

Сериализация межпроцессная: in-process mutex не видит другой процесс, поэтому sync и rollback дополнительно берут `flock` на файл `<data-dir>/locks/<hex(sha256("app/target"))>.lock`, где data-dir — каталог базы данных. Хеш нужен, потому что простое имя `app-target` сталкивается: app `a-b` с target `c` и app `a` с target `b-c` дают одно имя. Файловая блокировка берётся после mutex и освобождается при выходе из операции; ожидание опрашивает `LOCK_EX|LOCK_NB` и уважает ctx. Mutex остаётся быстрым путём: ожидающие одного target внутри процесса не опрашивают файл. Так `wormcd sync` и `wormcd server` на одном хосте с общей базой не запускают два apply одного target, и ограничение пункта 3 снято для процессов на одном хосте; надёжность `flock` между хостами не гарантируется, и этот вопрос остаётся открытым.

## Следствия

- Схема store не меняется: `targets` уникальна по `(app, target)`.
- `EnsureTarget` с пустым cluster не затирает существующее значение.
- Риск `ConfigUpdate` без optimistic lock снимается сериализацией sync в пределах процесса.
- Webhook и ручной sync (M3) используют тот же mutex.
- Нужен тест на два одновременных sync одного target (#20).

## Альтернативы

- **Ключ `(app, target, cluster)`**: позволяет один target катить в несколько кластеров, но усложняет историю и rollback, в v0 не нужно.
- **Lock в SQLite** (`BEGIN IMMEDIATE` на время apply или таблица locks): переживает перезапуск процесса, но удерживает write-lock на время apply, который может длиться минутами, и блокирует другие target.
- **Очередь sync с одним воркером**: проще рассуждать, но медленнее при нескольких target.
